# Credit Cards App

Credit cards microservice for the RF-006 requirement of Entrega 3. It
exposes the `/credit-cards/*` API and owns the `CreditCard` entity in its
own DynamoDB table, fully decoupled from every other component of the
platform.

This folder holds the application skeleton, the data model, the
persistence layer, the synchronous card creation flow (`POST
/credit-cards`), the user scoped listing flow (`GET /credit-cards`), and
the utility endpoints (`GET /credit-cards/count`, `GET /credit-cards/ping`,
`POST /credit-cards/reset`): bearer token validation against the users
application, request validation, duplicate and expiration rejection,
TrueNative tokenization, persistence as `POR_VERIFICAR`, the verification
event publish to the queue, the listing of the caller's cards, and the
unauthenticated count, ping, and reset operations.

## Data model

The `CreditCard` entity matches the information view exactly:

| Field | Data Type | Description |
|---|---|---|
| `id` | string | Card identifier in UUID format. Partition key of the table. |
| `token` | string (256 chars) | Token generated by the payment platform (TrueNative). |
| `userId` | string | Identifier of the user who owns the card. Partition key of the `userId-index` GSI. |
| `lastFourDigits` | string | Last four digits of the card. |
| `ruv` | string | Unique verification record generated by TrueNative. |
| `issuer` | string | Card issuer. Valid values: `VISA`, `MASTERCARD`, `AMERICAN EXPRESS`, `DISCOVER`, `DINERS CLUB`, `UNKNOWN`. |
| `status` | string | Card status. Valid values: `POR_VERIFICAR`, `RECHAZADA`, `APROBADA`. |
| `createdAt` | datetime | Date and time when the card was created. |
| `updatedAt` | datetime | Date and time when the card was last updated. |

The raw card number and the CVV are consumed by the tokenization call and
are never stored: the model does not even have fields for them. Dates
follow the entity contract: ISO `yyyy-mm-ddTHH:MM:SS` in UTC 0. The domain
model normalizes naive dates to UTC and converts aware dates to UTC on
construction, so every stored item honors the contract.

## The synchronous creation flow (POST /credit-cards)

The request must carry the caller bearer token in the
`Authorization: Bearer <token>` header and a JSON body:

```json
{
    "cardNumber": "4242424242424242",
    "cvv": "123",
    "expirationDate": "28/01",
    "cardHolderName": "Jane Doe"
}
```

| Field | Contract |
|---|---|
| `cardNumber` | Digits only, from 13 to 19 digits. |
| `cvv` | 3 or 4 digits. |
| `expirationDate` | Year and month in the `YY/MM` format, for example `28/01` (January 2028). The tolerant variant `YYYY/MM` is also accepted. |
| `cardHolderName` | From 1 to 100 characters. |

The flow, in the order of the RF-006 sequence view:

1. **Auth**: the token is validated against the users application
   (`GET /users/me`, synchronous HTTP/REST). The users application is the
   only authority for the token: this application has no access to its
   database. The answer also resolves the card owner (id and email; the
   email is the recipient of the result notification that the card worker
   will publish).
2. **Validation**: the request fields are checked (400 for a missing,
   empty, or malformed field) and the expiration date is checked against
   the current date (412 when the card is already expired; a card
   expiring in the current month is still valid through the end of the
   month).
3. **Duplicate check**: the caller's stored cards are looked up in its own
   DynamoDB table (one query on the `userId-index` GSI). The raw card
   number is never persisted, so the stored identity of a card is its last
   four digits: the same card submitted twice by the same user is
   rejected with 409.
4. **Tokenization at TrueNative**: `POST /native/cards` with the `card`
   object (the `cardNumber` and the `cvv` travel only inside this request,
   with the expiration normalized to `MM/YYYY`) and a unique
   `transactionIdentifier`, authenticated with the
   `Authorization: Bearer <SECRET_TOKEN>` header. The platform returns
   the RUV, the token, and the issuer derived from the card BIN.
5. **Issuer**: the issuer returned by TrueNative is used when it is a
   valid value of the documented enum; otherwise the application falls
   back to its own BIN detection, which ends in `UNKNOWN` for
   unrecognized prefixes.
6. **Persistence**: the card is stored with `status = POR_VERIFICAR`,
   together with the token, the last four digits, the RUV, the issuer,
   and the creation and update dates.
7. **Event publish**: the verification event (card id, RUV, the stored
   card data, and the owner email resolved in step 1) is sent to the SQS
   queue, which hands it to the card worker (a separate component; this
   application never runs async work).
8. **Answer**: `201` with `{id, userId, createdAt}`. The path performs
   only one token validation, one TrueNative call, one database write, and
   one queue publish, so it completes within the 5 second budget without
   waiting for the verification.

### Response

`201 Created`:

```json
{
    "id": "a card uuid",
    "userId": "the owner uuid",
    "createdAt": "2026-09-23T02:30:00"
}
```

### Error contract

| Status | When |
|---|---|
| `400` | A field is missing, empty, or malformed. |
| `401` | The token is invalid or expired (passed through from the users application), or the `Authorization` header uses a scheme other than Bearer. |
| `403` | The request carries no bearer token at all. |
| `409` | The caller already stored the same card. |
| `412` | The card is already expired. |
| `502` | The users application cannot be reached or answers unexpectedly, or TrueNative cannot register the card or generate the token (bad secret token, malformed request, a verification already in progress, or any other failure). In that case nothing is stored. |

The queue publish never fails the request: if the queue is not configured
or cannot be reached, the failure is logged and the card stays
`POR_VERIFICAR`, which is a valid state. Failing the user request after a
successful tokenization would turn the retry into a duplicate conflict.

## The user scoped listing flow (GET /credit-cards)

The request must carry the caller bearer token in the
`Authorization: Bearer <token>` header. There is no request body.

The flow:

1. **Auth**: the token is validated against the users application (the
   same dependency as the creation flow: 403 without a token, 401 with an
   invalid or expired token). The users application is the only authority
   for the token: this application has no access to its database.
2. **User scoped query**: the caller's stored cards are read from the
   DynamoDB table with a single query on the `userId-index` GSI, filtered
   by the caller id. The query always carries the caller id, so cards
   belonging to other users are never returned.
3. **Answer**: `200` with the JSON array of the caller's cards (an empty
   array when the caller has not stored any card yet).

### Response

`200 OK` (a JSON array, one item per stored card):

```json
[
    {
        "id": "a card uuid",
        "token": "the payment token generated by TrueNative",
        "userId": "the owner uuid",
        "lastFourDigits": "4242",
        "issuer": "VISA",
        "status": "POR_VERIFICAR",
        "createdAt": "2026-09-23T02:30:00",
        "updatedAt": "2026-09-23T02:30:05"
    }
]
```

| Field | Contract |
|---|---|
| `id` | Card identifier in UUID format. |
| `token` | Payment platform token. The API contract of the exercise includes it in the listing for educational purposes; a real service would never expose it. |
| `userId` | Owner user identifier, always equal to the caller. |
| `lastFourDigits` | Last four digits of the card number. |
| `issuer` | Card issuer (documented enum value). |
| `status` | Card status (`POR_VERIFICAR`, `RECHAZADA`, `APROBADA`). |
| `createdAt` | Creation date in ISO `yyyy-mm-ddTHH:MM:SS`, UTC 0. |
| `updatedAt` | Last update date in the same ISO format. |

The raw card number and the CVV are not stored by this application, so
they cannot appear in the listing. The RUV is not returned either: it is
internal to the asynchronous verification (the card worker polls
TrueNative with it).

### Error contract

| Status | When |
|---|---|
| `401` | The token is invalid or expired (passed through from the users application), or the `Authorization` header uses a scheme other than Bearer. |
| `403` | The request carries no bearer token at all. |

## Storage

The application owns a dedicated DynamoDB table, provisioned by the
`3_dynamodb` Terraform stack:

- partition key `id` (the card UUID), used by the asynchronous worker to
  update the status by id;
- global secondary index `userId-index` (partition key `userId`, projection
  `ALL`), which turns the per owner listing and the duplicate check into a
  single query;
- on demand billing (`PAY_PER_REQUEST`) and server side encryption.

The table is exclusive to this component. No other application of the
platform reads it directly; the card worker (`card_worker`, consumed by
the `5_sqs` queue and deployed by the `6_lambda` stack) is the only unit
that updates it, and it talks to the same DynamoDB API. The legacy
applications keep their shared RDS PostgreSQL instance and never touch
this table.

## Utility endpoints (count, ping, reset)

The three utility endpoints of the API specification require no bearer
token. They are the mechanism the grading pipeline uses to set up and
check state between runs, so the exact contract fidelity matters.

- `GET /credit-cards/count` answers `200` with `{"count": <n>}`, the
  current number of stored cards.
- `GET /credit-cards/ping` answers `200` with the plain text body `pong`
  (not a JSON string), the same contract as the TrueNative liveness
  probe. The image health check uses this route.
- `POST /credit-cards/reset` deletes every stored card and answers `200`
  with the exact documented message `{"msg": "Todos los datos fueron
  eliminados"}`; the string is not translated.

## Testing

Unit tests run against an in memory DynamoDB table and an in memory SQS
queue created by the moto library (the fixtures mirror the schema of the
`3_dynamodb` stack and the queue contract of the worker task); the HTTP
adapters are tested with the `httpx2` mock transport, so no AWS account
and no network access are required.

```bash
cd credit_cards_app
poetry run pytest --cov=src --cov-fail-under=70 -v
```

**Results**: 173 tests pass with 99% coverage.

Dates in the tests are computed at test time (relative offsets from
`datetime.now(timezone.utc)`); no fixed date is hardcoded, so the suite
cannot expire.

## Manual verification

The full reproducible steps live in the Manual verification of RF-006
section of
[development-view.md](../docs/development-view.md#manual-verification-of-rf-006).
The short form:

**AWS dev environment (full flow).** With the platform deployed, the script
below asserts the infrastructure of the asynchronous flow, the synchronous
contract of `POST /credit-cards` (403, 401, 400, 412), the utility
endpoints without a token (the ping body `pong`, the count field), the
asynchronous seam (`POR_VERIFICAR` right after the `201`, then `RECHAZADA`
with `SUCCESS_RATE=0` and `APROBADA` with `SUCCESS_RATE=100`, an empty
queue and an empty dead letter queue, watched through the listing endpoint
`GET /credit-cards`), the listing contract itself (the caller's array
carries the stored card with the documented fields, the dates in ISO
format), the duplicate rejection (409), and the result email notification
(TASK-023): the worker publishes the result, the stored card basics and the
RUV to the SNS topic after every terminal state, for both outcomes, which
the script reads from the CloudWatch log group of the function. The final
cleanup uses `POST /credit-cards/reset` (the exact documented message, the
count back to 0), with the item by item table deletion as fallback. It
exits 0 only when every check passes.

```bash
bash scripts/terraform_scripts/verify-aws-rf006.sh
```

**Local Minikube (partial flow).** The cluster has no DynamoDB table, no
SQS queue, and no Lambda function, so only the answers that resolve before
the first DynamoDB call are asserted: deployment and service ready, ingress
routing through the liveness probe `GET /credit-cards/ping` (200 with the
body `pong`), the 403, 401, 400 and 412 responses of the creation endpoint,
plus the same auth contract of the listing endpoint `GET /credit-cards`
(403 without a token, 401 with an invalid token). The `200` answers that
need the table (the listing, the count, and the reset) are covered by the
AWS steps above.

```bash
bash scripts/local-deploy.sh
bash scripts/local-verify.sh
```

## Definition of done for the creation flow (TASK-021)

- `POST /credit-cards` implements the full synchronous flow: bearer token
  validation against the users application (no direct access to its
  database), request validation, duplicate rejection (409), expired card
  rejection (412), TrueNative registration with a unique
  `transactionIdentifier`, persistence as `POR_VERIFICAR`, verification
  event publish to the queue, and the `201 {id, userId, createdAt}`
  answer in under 5 seconds.
- The raw card number and the CVV are never persisted; only the last four
  digits, the issuer, the token, the RUV, and the status are stored.
- A TrueNative tokenization failure stores nothing and answers 502.
- No asyncio, threads, or background tasks run inside this component; the
  slow verification is handed off through the queue to the card worker.

## Definition of done for the listing flow (TASK-024)

- `GET /credit-cards` answers 200 with the JSON array of the caller's
  stored cards; each item carries `id`, `token`, `userId`,
  `lastFourDigits`, `issuer`, `status`, `createdAt`, and `updatedAt`,
  with the dates in ISO format (yyyy-mm-ddTHH:MM:SS, UTC 0).
- A request without any bearer token answers 403, and an invalid or
  expired token answers 401 (the same contract as the creation endpoint,
  resolved against the users application).
- Cards belonging to other users are never returned: the listing query is
  always filtered by the caller id (a single query on the `userId-index`
  GSI), and the unit tests cover both the user scoping and the contract
  fields.
- The creation endpoint is unchanged; the raw card number and the CVV are
  not in the answer (they are not stored by this application).

## Definition of done for the utility endpoints (TASK-025)

- `GET /credit-cards/count` answers 200 with `{"count": <n>}`, the current
  number of stored cards, without any authentication.
- `GET /credit-cards/ping` answers 200 with the plain text body `pong`
  (not a JSON string), without any authentication; the image health check
  uses this route.
- `POST /credit-cards/reset` deletes every stored card and answers 200
  with the exact documented message
  `{"msg": "Todos los datos fueron eliminados"}`, without any
  authentication; the message is not translated.
- The unit tests cover the no auth access, the count against a table with
  stored cards, and the reset deleting every card (the count back to 0 and
  the listing back to an empty array).
