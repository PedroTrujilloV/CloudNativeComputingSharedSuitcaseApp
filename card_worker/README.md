# Card Worker

Card verification worker for the RF-006 requirement of Entrega 3. It is an
AWS Lambda function (packaged as a container image) that consumes the card
verification queue (SQS), polls TrueNative until the card reaches a
terminal state (`APROBADA` or `RECHAZADA`), updates the card status and
`updatedAt` in the DynamoDB table owned by `credit_cards_app`, and publishes
the mandatory email notification of the result to the SNS topic of the
`4_sns` stack (result, stored card basics, and the RUV).

This component is what satisfies both the event driven asynchronous
requirement and the no async in thread restriction at the same time: the
credit cards web application publishes the event and answers the client in
under 5 seconds, and this separate deployable unit does the slow work
outside of that process. The function itself is plain synchronous code
invoked by the queue, so no background task, thread, or asyncio runs
anywhere.

## Requirements

- Python 3.11
- Poetry 2.1.1
- AWS credentials from the execution role of the Lambda function (standard
  boto3 chain; nothing is hardcoded)

Runtime dependencies (installed via `poetry install`):

- boto3: DynamoDB client
- httpx2: HTTP client for the TrueNative polling calls
- pydantic: validation of the queue event contract

Development dependencies (managed in the `dev` dependency group):

- pytest: test runner
- pytest-cov: coverage reporting
- moto: in memory AWS emulation for the unit tests

## How it works

The `6_lambda` Terraform stack creates the Lambda function with this image
and an SQS event source mapping on the card verification queue
(`5_sqs` stack). Every invocation receives the records of the queue
(`batch_size` 1, one card per invocation):

1. **Parse the record**: the body is the `CARD_VERIFICATION_REQUESTED`
   event published by `credit_cards_app` (cardId, ruv, userId,
   lastFourDigits, issuer, status, createdAt, and the owner email, which
   the credit cards application resolved through the users application
   API). A record that does not match the contract is rejected.
2. **Bounded polling**: the use case polls `GET /native/cards/{ruv}` with
   the `Authorization: Bearer <SECRET_TOKEN>` header, up to
   `POLL_MAX_ATTEMPTS` times with `POLL_INTERVAL_SECONDS` between attempts
   (defaults: 5 and 2). A `202` answer means the platform is still
   processing, so the loop waits and retries; a `200` answer carries the
   terminal status.
3. **Persist the terminal state**: on `200`, the worker sets the card
   status and refreshes `updatedAt` to the current UTC time, by card id.
   The update is idempotent under the at least once delivery of the queue:
   a card that already carries the same terminal state is not rewritten.
4. **Notify by email**: right after the persist, the worker publishes the
   result notification to the SNS topic (`CARD_RESULT_TOPIC_ARN`, the
   `grupo33-card-verification-notifications` topic of the `4_sns` stack).
   The message carries the process result, the basic card data as stored
   in the database (id, last four digits, issuer, updated date), the RUV
   generated by TrueNative, and the recipient address; the raw card number
   and the CVV never appear in it. The topic subscription uses the email
   protocol, so SNS performs the actual delivery to the address read from
   the `EMAIL_TO_NOTIFY` key of the `secrets-pipeline-native-map` secret.
   A publish failure raises, so the queue redelivers the event and the
   notification is retried on the next invocation (the status update is
   idempotent, so the retry is safe). While the topic ARN is empty the
   publish is skipped and logged, so the worker can run before that
   wiring is in place.

### Fallback (no terminal state within the budget)

If the bounded attempts are exhausted (for example TrueNative is slow or
unreachable), the invocation fails on purpose: the queue redelivers the
event, and the card stays `POR_VERIFICAR`, which is a valid state. On the
last receive (the one after which the event moves to the dead letter
queue, detected through the `ApproximateReceiveCount` attribute of the
SQS record and the `MAX_RECEIVE_COUNT` setting that mirrors the
`maxReceiveCount` of the redrive policy of the `5_sqs` stack) the worker
publishes the mandatory `POR_VERIFICAR` notification first, with the same
content and the same recipient, so the owner is never left without the
email. That fallback publish failure is logged instead of raised, because
the invocation fails anyway and the event moves to the dead letter queue
for operator inspection either way; the card remains `POR_VERIFICAR`. This
fallback is a team decision, documented in the solution patterns view; it
keeps the card in a valid state without ever losing the event.

### Least privilege

The worker runs under its own execution role (the `6_lambda` stack grants
exactly what it uses): `dynamodb:GetItem` and `dynamodb:PutItem` on the
credit cards table only, `sqs:ReceiveMessage`, `sqs:DeleteMessage`, and
`sqs:GetQueueAttributes` on the card verification queue only,
`sns:Publish` on the card verification topic only (the result email
notification), and CloudWatch log writes scoped to the function log group.
The `SECRET_TOKEN` value is injected by the stack from the
`secrets-pipeline-native-map` secret in AWS Secrets Manager and never
appears in this repository.

## Environment variables

| Variable | Default | Description |
|---|---|---|
| `APP_NAME` | `card_worker` | Application name (logging). |
| `LOG_LEVEL` | `INFO` | Logging level. |
| `AWS_REGION` | `us-east-1` | Region of the DynamoDB table. |
| `DYNAMODB_TABLE_NAME` | `credit_cards` | Name of the credit cards table (injected by the `6_lambda` stack from the `3_dynamodb` output). |
| `TRUENATIVE_URL` | `http://truenative-service` | Base URL of the TrueNative platform. In the cloud it is the single external host of the platform (the ingress load balancer, `https://...`), discovered by the `6_lambda` stack. |
| `TRUENATIVE_SECRET_TOKEN` | (empty) | Secret token of TrueNative, injected by the `6_lambda` stack from the `secrets-pipeline-native-map` secret. |
| `CARD_RESULT_TOPIC_ARN` | (empty) | ARN of the SNS topic of the card result email notification; while empty the publish is skipped and logged (the worker can run before the notification wiring is in place). |
| `POLL_MAX_ATTEMPTS` | `5` | Bounded attempts per invocation. |
| `POLL_INTERVAL_SECONDS` | `2` | Wait between two attempts. |
| `HTTP_TIMEOUT_SECONDS` | `3` | Timeout of each polling request. |
| `MAX_RECEIVE_COUNT` | `5` | Receives before the redrive to the dead letter queue; must mirror `max_receive_count` of the `5_sqs` stack (on that last receive the worker publishes the `POR_VERIFICAR` fallback email). |

## Execution

### As a Lambda function (production)

The function is image based: the `Dockerfile` builds on the SAM Python
3.11 base image, the application code lives in `/var/task`, and the handler
is declared with `CMD ["handler.handler"]`. The `6_lambda` stack consumes
the image from ECR (`card-worker` repository, `v0.0.0` tag per
`config.yaml`) and wires the queue, the role, and the environment.

### Local build

```bash
cd card_worker
poetry install
docker build -t card-worker:v0.0.0 .
```

To exercise the handler locally, run any Python 3.11 shell with
`PYTHONPATH=src` and call `handler.handler` with an SQS shaped event, for
example:

```python
import json
from handler import handler

event = {
    "Records": [
        {
            "body": json.dumps(
                {
                    "eventType": "CARD_VERIFICATION_REQUESTED",
                    "cardId": "11111111-1111-4111-8111-111111111111",
                    "ruv": "ruv-1",
                    "userId": "user-1",
                    "lastFourDigits": "4242",
                    "issuer": "VISA",
                    "status": "POR_VERIFICAR",
                    "createdAt": "2026-01-01T00:00:00",
                    "ownerEmail": "owner@example.com",
                }
            ),
            "messageId": "m-1",
        }
    ]
}
handler(event, None)
```

(the example needs the AWS environment of the table and the TrueNative
host reachable, or the credentials of the execution role).

## Testing

```bash
cd card_worker
poetry install
poetry run pytest --cov=src --cov-fail-under=70
```

The unit tests run against an in memory DynamoDB table (moto), an in
memory SNS topic (moto) for the notification publisher, and a mock HTTP
transport for the TrueNative calls; the wait between polling attempts is
injected and recorded, so the suite never sleeps and never hardcodes
dates.
