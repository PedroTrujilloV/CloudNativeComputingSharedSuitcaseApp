# Card Worker Lambda Stack (6_lambda)

## Overview

The **6_lambda** stack provisions the consuming side of the asynchronous
seam of RF-006: the `card_worker` Lambda function (image based, built from
the `card_worker` folder per `config.yaml`) and the SQS event source
mapping that connects it to the card verification queue created by the
`5_sqs` stack.

The academic lab accounts do not allow `iam:CreateRole` or
`iam:PutRolePolicy`, so the function does not create its own least
privilege execution role: it uses the `LabRole` that every lab account
provisions in advance (the role allows the integrations of the flow).

The worker consumes the `CARD_VERIFICATION_REQUESTED` events, polls
TrueNative `GET /native/cards/{ruv}` a bounded number of times per
invocation, and updates the terminal status and `updatedAt` of the card in
the DynamoDB table owned by `credit_cards_app`.

## Why this stack is in post_k8s_stacks

The function is image based and its `image_uri` points to the worker image
that the deploy pipeline builds and pushes to ECR in the
`build-and-push-images` job, which runs after the `terraform` job of the
`tf_stacks`. An image based Lambda cannot be created before its image
exists in ECR, so this stack is applied in `post_k8s_stacks`
(`config.yaml`), after both the image push and the k8s deploy. The queue
itself lives in the `5_sqs` stack (in `tf_stacks`) because the credit
cards manifest needs the queue URL at envsubst time.

Note that the worker does **not** receive the host of the ingress load
balancer as an environment variable: that balancer is created by the EKS
cloud controller manager once the k8s manifests are applied, its name is
generated by the cluster, and the deploy pipeline does not expose it to
this stack. The worker discovers the host at runtime through the ELBv1
API (see "Execution role"), so this stack needs no data source for
the balancer.

## Components

| Resource | Description |
|---|---|
| **Lambda function: card worker** | Image based function (`card-worker` repository of ECR, tag per `config.yaml`). Timeout 30 s, memory 256 MB. Environment: table name, `TRUENATIVE_SECRET_TOKEN` (from the `SECRET_TOKEN` key of the `secrets-pipeline-native-map` secret, never committed), card topic ARN, and the bounded polling settings. The TrueNative host is not an environment variable: the worker discovers the ingress load balancer at runtime. |
| **SQS event source mapping** | Invokes the function on the card verification queue with `batch_size` 1 (one card per invocation, clean idempotency) and no batching window (the event is delivered as soon as it is visible). |

## Execution role

The academic lab accounts do not allow `iam:CreateRole` or
`iam:PutRolePolicy`, so this stack does not create the execution role of
the function: the `role` argument of `aws_lambda_function` points to the
`LabRole` that every lab account provisions in advance
(`arn:aws:iam::<account>:role/LabRole`, built from the caller identity at
plan time). The lab role allows the integrations of the flow:

* `dynamodb:GetItem` and `dynamodb:PutItem` on the credit cards table.
* `sqs:ReceiveMessage`, `sqs:DeleteMessage`, and `sqs:GetQueueAttributes`
  on the card verification queue.
* `sns:Publish` on the card verification topic (the result notification of
  the epic; the permission is granted now so the next task only adds the
  publish call in the code).
* `elasticloadbalancing:DescribeLoadBalancers` and
  `elasticloadbalancing:DescribeTags` on the classic load balancers of the
  account: the worker discovers the host of the ingress load balancer at
  runtime (the balancer is created by the EKS cloud controller manager,
  not by Terraform, and its name is not known at plan time).
* `logs:CreateLogGroup`, `logs:CreateLogStream`, and `logs:PutLogEvents`
  on the log group of this function only.

The `TRUENATIVE_SECRET_TOKEN` value is read at plan time from the
`SECRET_TOKEN` key of the `secrets-pipeline-native-map` secret in AWS
Secrets Manager (populated by the pipeline from the environment
secrets; see `terraform/stacks/eks/README.md`) and injected as an
environment variable; the k8s side gets the same value through the
base64-encoded `secret_token_b64` output of the `eks` stack, so both
sides always match, and the token never appears in this repository.

## Timing model

One invocation polls up to `poll_max_attempts` times (5) with
`poll_interval_seconds` (2 s) between attempts and `http_timeout_seconds`
(3 s) per request, so the worst case invocation is under the 30 s timeout.
When the attempts are exhausted the invocation fails on purpose, the queue
redelivers the event (visibility timeout 45 s in `5_sqs`), and the card
stays `POR_VERIFICAR`; after `maxReceiveCount` receives the event is moved
to the dead letter queue (documented fallback of the RF-006 pattern).

## Plan prerequisites

* The worker image must exist in ECR with the tag declared in
  `image_tag` (the deploy pipeline pushes it in the
  `build-and-push-images` job, which is why this stack is in
  `post_k8s_stacks`).
* The `5_sqs` and `4_sns` stacks must be applied (the queue and the topic
  must exist to resolve their ARNs).
* The `secrets-pipeline-native-map` secret must exist (the pipeline
  creates it from the environment secrets before applying any stack;
  this stack reads its `SECRET_TOKEN` key).
